# Nafs-Aql operator runbook

This runbook is for whoever installs, runs and maintains a Nafs-Aql deployment. It covers the two supported profiles:

- **Reference machine:** llama-server on macOS or a Linux AVX2 host.
- **Linux vLLM-CPU:** docker compose.

## 1. Install

| Step | Reference machine (macOS or Linux AVX2) | Linux vLLM-CPU |
|---|---|---|
| Models | `scripts/fetch_models.sh` (GGUF, about 3.6 GB) | pulled by vLLM on first start (Hugging Face cache volume) |
| Build | `cd rust && cargo build --release` | `docker compose -f deploy/docker/docker-compose.yml build` |
| Secrets | `export NAFS_AUTH_TOKENS_FILE=/path/to/tokens` (one token of 16 or more characters per line) | write `deploy/docker/secrets/nafs_tokens` |
| Start | `make up`, or the launchd / systemd files in `deploy/launchd/` and `deploy/systemd/` | `NAFS_DOMAIN=your.host docker compose -f deploy/docker/docker-compose.yml up -d` |
| TLS | put `deploy/tls/Caddyfile` or `deploy/tls/nginx.conf` in front of 127.0.0.1:8080 | the `proxy` service (Caddy) terminates TLS |
| Verify | `scripts/verify_deploy.sh --live` and `rust/target/release/nafs-gateway --check` | the same, from the host |

**vLLM in Docker (reference machine).** `scripts/serve_vllm_docker.sh start && scripts/serve_vllm_docker.sh wait` serves Qwen3-1.7B in BF16 on :8101 from the `carstenz/vllm-smoke:0.1.0-cpu` image, as the gateway's `vllm` backend set expects; switch with *Use this backend* on the System page and check it with `python3 scripts/vllm_check.py`. The Docker VM needs about 6 GiB free (10 GiB allocated here). Expect a load time of several minutes and, on four shared cores, slower decoding than llama-server.

**Linux hosts and the code sandbox.** Verifying model-written code needs unprivileged user, network, mount and PID namespaces, `unshare` and `setpriv` (util-linux) and a python3 with ctypes (the seccomp stage). It hides user data (`/home`, `/tmp`, `/run/secrets` and others), makes the rest of the filesystem read-only and denies `fork`; the gateway's own install, config and data directories stay readable (not writable), so keep them mode 0700 under a dedicated user (A-054). Stock Ubuntu 24.04 blocks them (`kernel.apparmor_restrict_unprivileged_userns=1`); `nafs-gateway --check` then reports `sandbox_isolation: false` and code verification fails closed. Enable them with `sudo sysctl -w kernel.apparmor_restrict_unprivileged_userns=0` (persist it in `/etc/sysctl.d/`), or run the gateway in the provided compose file, which relaxes seccomp and AppArmor for the same reason (A-040).

The gateway refuses to listen on a non-loopback address without tokens (SR-006). Set `NAFS_ALLOW_INSECURE=1` only on an isolated lab network. Browsers must reach the gateway on the same origin. For any other host name, set `NAFS_ALLOWED_HOSTS` or enable tokens.

## 2. Daily operation

- **Health:** `GET /healthz` reports `ok`, or `degraded` when System 2 is down. In degraded mode, answers fall back to the unverified System 1 draft (MR-004).
- **Dashboards:**
  - Prometheus scrapes `/metrics`; the rules are in `deploy/monitoring/alerts.yml` and the dashboard in `deploy/monitoring/grafana-dashboard.json`.
  - Without Prometheus, the Muhasaba page shows the same five alert rules: fast-path latency, error rate, escalation rate, verifier acceptance and calibration drift.
  - The alerts describe live traffic only. Evaluation runs and load-test protocols started from the Lab or Performance pages are stored as lab traffic and do not trigger them (A-043).
- **Alert drill:** press *Run alert drill* on the Muhasaba page, or call `POST /v1/alerts/drill {"seconds": 120}`. Every rule reports firing for two minutes, so notification paths can be tested.
- **Retention:** conversations, replies, feedback, audits and the retrieval memory older than `storage.retention_days` (default 90) are deleted daily (SR-004).
- **Restarts:** evaluation runs interrupted by a restart resume automatically, keeping their completed items. You can also resume one with the Resume button or `POST /v1/eval/runs/{id}/resume`.
- **Shared hosts:** llama-server, vLLM and the gateway compete for the same cores. Run one backend set at a time, and check `uptime` before benchmarking.
- **Latency:** `GET /v1/perf/stages?hours=24` (or the Performance page) attributes wall time to stages and reports prefill and decode speed and KV-cache reuse per model stage. A falling decode rate with an unchanged cache-reuse share usually means CPU contention from other processes.
- **Rooms:** a gateway keeps at most 500 rooms, 64 members per room, and queues at most three questions behind the running one; messages over 8,000 characters are refused. Deleting a room (`DELETE /v1/rooms/{id}`, or *Delete* in the header) permanently removes the room and the replies, decisions, feedback and retrieval-memory entries made from it, disconnects its members and cancels a running answer. Rooms are not touched by the retention purge and have no access control beyond the gateway's own tokens and Origin check, so treat anyone who can reach the gateway as able to administer every room. `python3 -I scripts/rooms_test.py [--slow]` exercises the whole feature against a running gateway and removes the rooms it creates.
- **Knowledge bases (Phase 20):** `[knowledge]` needs SurrealDB (`scripts/serve_surreal.sh start`, 127.0.0.1:8300, root password in `data/runtime/surreal/root.secret`) and, for search by meaning, the embedding server (`scripts/serve_smiley.sh embed`, :8203); `GET /v1/kb/status` reports both. Originals live in `files_dir` (`data/runtime/kb/<base>/`), passages, vectors and the graph in SurrealDB. Ingestion runs on two lanes: a document is `ready` by its words as soon as it is stored, and its vectors and graph follow on a slow lane, one job at a time, so a small upload never waits behind a large re-index. **The slow lane's queue is in memory:** a restart loses queued vector and graph jobs; `POST /v1/kb/{kb}/reindex` and `POST /v1/kb/{kb}/graph/build` start them again, and a restart while a document is `embedding` re-reads it and its vectors are made again. The graph build costs about a minute per passage of quick-model time on four cores; run it when the host is quiet. A base made before Phase 21 gets its words index migrated on first use (the log says so); `reindex?fresh=true` recomputes its vectors with the context lines. `python3 -I scripts/kb_sweep.py [--kb <id>] [--no-chat]` exercises the whole feature against a running gateway and removes the scratch base it creates.
- **Knowledge hardening (Phase 8):** uploads are bounded (`max_upload_mb` per file, `max_request_mb` per request, `concurrent_uploads` received at once; a refused request is a 413, a busy server a 429 with code `busy`); a base holds `max_documents_per_base` documents, a document makes `max_chunks_per_document` passages (larger files must be split), `max_queued_jobs` jobs may wait, a parser has `parse_timeout_s` seconds, and `max_concurrent_trainers` training runs go at once across all bases. `GET /v1/kb/status` shows the limits in force. **Deleting** a base (`DELETE /v1/kb/{kb}`) stops its training runs, takes it out of use at once (its rows are removed in the background, about 16 passages a second, so a 50,000-passage base takes under an hour; a restart resumes an interrupted deletion), removes its rows, its folder (originals, runs, activated modules) and what the memory reader held in memory, and removes the passages from the ledger's stored replies (the response counts `replies_scrubbed` and `trainers_stopped`); deleting a document does the same for that document. A base's conversations are not touched. A hybrid search fuses the words and the meaning by rank with the meaning weighted `vector_weight` (0.1) and gives up on the words after `search_timeout_s` (10) when a very common word makes the store score most of a large base (the answer is then by meaning alone, and says so); function words are left out of a words search. `python3 -I scripts/kb_retrieval_rank.py --kb <id> [--questions f.json] [--fusion-sweep]` ranks where the answering passage lands and sweeps the weight, in seconds. Chat uses a passage when its meaning similarity reaches `rag_min_similarity` or its words match at `rag_lexical_rescue` (BM25 score 10.0; 0 turns the rescue off; raise it for a much larger base). `scripts/kb_security_run.sh [--chat]` starts a throw-away gateway on :8093 with small limits and its own database, runs `scripts/kb_security_sweep.py` against it and stops it; `scripts/live_sweep.sh kbsec` does the same. `[knowledge] vector_cache_mb` (default 0) turns on an exact in-memory copy of a large base's vectors (20 ms a search, 200 MB per 50,000 passages, minutes to load on first use, words-only answers meanwhile); the store's HNSW index, the default, answered in 0.37 s at the median at 50,000 passages once warm. `NAFS_KB_SCALE=1 cargo test --release -p nafs-kb --test scale_it -- --nocapture` builds a 1,000-document, 50,000-passage base in a scratch database and times what a person waits for.
- **Memory of earlier conversations (Phase 26):** `[recall]` is on by default. Each finished turn of a stored conversation becomes a note in the `episodes` table of `nafs.sqlite` (so it is covered by the same backup); private requests, rooms and the Lab write and read nothing. Notes are read only when a question is in the first person or points back, at most `limit` (3) notes and `budget_chars` (1,500) characters. `GET /v1/memory` lists them, `DELETE /v1/memory/{id}` forgets one, `DELETE /v1/memory` all, `POST /v1/memory/tidy` merges repeated ones; a person does the same under Settings → Memory. `max_episodes` (5,000) bounds the table; the retention purge removes the notes of the conversations it removes. There are no accounts: on a shared installation everyone who can reach the service shares this memory, so set `enabled = false` there or run it behind access keys. Counters: `nafs_recall_notes_total`.
- **Knowledge settings added in Phase 26:** `fuzzy_terms` (a mistyped question word is matched to the nearest word of the base), `followup_context` (a follow-up question is searched with the previous turn), `support_check` (each answer from documents lists the sentences that are not in its passages; counters `nafs_knowledge_claims_total` and `nafs_knowledge_claims_unsupported_total`), `support_escalate_below` (0 = off: send a quick answer below this supported share to the reasoning model), `rag_elbow_gap` (0 = off). A base whose vectors were written by another embedding model than `embed_model` is searched by words and says so; *Rebuild the meaning index* (`POST /v1/kb/{kb}/reindex?fresh=true`) fixes it. A memory module that gives every question the same memory is not used (the log line says `memory module collapsed`); train again with the defaults, which are now the reference recipe.
- **Gate settings added in Phase 22:** `gate.max_risk` (0.15) is the certified error bound a calibration bin must meet for a draft to be kept in calibrated mode (`GET /v1/gate/calibration` lists the bins and their bounds; a calibration fitted before Phase 22 has none and is not promoted until `POST /v1/gate/calibrate` refits it); `gate.on_unknown` (`escalate`, `keep` or `fixed`) decides a draft with no log-probabilities, which a backend without them produces; `gate.reask_overlap` (0.6) and `gate.reask_escalates` treat a repeated question as a sign the last answer failed.
- **Speed changes:** adopt a serving flag or weight format only after an interleaved A/B (NFR-031); `scripts/perf_tuning.sh` and `scripts/early_escalation_study.py` record theirs. Early escalation is tuned with `gate.early_escalation_tokens` and `gate.early_escalation_margin` (0 tokens turns it off). Phase 8 adds the lowest-window confidence signal: `gate.confidence_window` (16 tokens), `gate.fixed.low_window_logprob_threshold` (absent = off; set from `benchmarks/confidence_signal_study.json`, re-run `scripts/confidence_signal_study.py` after a model change) and `gate.fixed.low_window_domains` (the domains where the threshold was measured; the signal's scale differs between prose and mathematics). A draft is stopped the moment a window crosses the threshold, and the decision is the one the full draft would get, so no agreement study is needed for this rule. The adaptive exit's stopping rule on non-verifiable tasks is `deliberation.adaptive_exit.exit_rule` (`consistency` or `posterior`, with `posterior_stop` and `posterior_stop_end`), overridable per request with `"adaptive_exit_rule"`. The adaptive reasoning exit (`[deliberation.adaptive_exit]`) shortens System 2 reasoning by probing for the answer and verifying it; it needs llama-server (vLLM uses the standard path) and can be switched off per request with `"adaptive_exit": false`. EAGLE-3 heads are opt-in (`EAGLE=1`) and were not adopted on the reference CPU; re-measure with `scripts/eagle3_ab.py --system 1|2` on another host.

**Capacity on a 4-core CPU host.** (Phase 17: Smiley Core runs three decode threads by default, `THREADS=4` on a quiet host, and keeps up to 768 MB per model of earlier prompts' caches, so switching between kinds of request is free.) (Phase 15: the default engine is Smiley Core, one stream per model, so a second concurrent request waits; for two or more simultaneous users run `make up-llama`, which has the four slots described next.) Plan for one user at a time: fast path p50 0.6 to 0.9 s and p95 1.1 to 1.4 s on short chat, slow path about one minute on a GSM8K-class question. Two concurrent sessions cost 1.7 to 2.0x the single-session p95; four cost 3.4 to 3.9x, because the decode batch is compute-bound on four cores. Recommended limit: 2 concurrent sessions (decision 002, `benchmarks/slots_ab_system1.json`); more users need the GPU profile. **System 2 slots (Phase 13):** System 2 is served with 4 slots and 24,576 tokens of context (`scripts/serve_llama.sh`, `S2_SLOTS`, `S2_CTX`; the systemd and launchd units match, and `backends.llama.system2.max_in_flight = 4`), because the 100-prompt run lost 476 s waiting for a slot. The 2-session limit stays: four System 2 streams decode only 1.5x the tokens of one at the 1,600-token depth of a repair prompt (`docs/research/parallel_inference.md`). **Before escalating**, a failed draft on a checkable task draws 4 concurrent System 1 samples (`gate.rescue_samples`, 0 turns it off); `GET /v1/harness` reports it with the parallel settings.

## 3. Alerts and what to do

| Alert | Likely cause | Action |
|---|---|---|
| Fast-path latency high | host overloaded, too many concurrent sessions, model swapped out | check `uptime` and memory pressure; reduce concurrency; NFR-007 is documented as failing above 1–2 sessions on a 4-core CPU |
| Error rate high | a backend down or timing out | `scripts/serve_llama.sh status`; restart the failing server; read `logs/system*.log` |
| Escalation rate high | gate too cautious (λ low), harder traffic, uncalibrated rule | review the Lab insights; raise λ or switch to budget mode once a calibration is promoted |
| Verifier acceptance low | model regression, prompt change, broken tests | run the regression suite; compare with the baseline run |
| Calibration drift | the traffic or the model changed | recalibrate (Muhasaba page); confirm on a fresh evaluation run |
| Degraded mode | System 2 unavailable | restart System 2; answers are labelled unverified meanwhile |

## 4. Changes and releases

1. Every model, adapter, template or configuration change runs the regression suite: `regression_500`, with fast_only for System 1 changes (ER-008).
2. Model promotion: `python3 training/tazkiya.py promote …`, then restart serving. Rollback: `python3 training/tazkiya.py rollback`, then restart (OR-005).
3. Release archive: `scripts/package_release.sh`, which produces binaries, schemas, the model manifest, deployment recipes and SHA256SUMS (OR-002).
4. Security: `python3 -I scripts/security_tests.py` must report 0 open high-severity findings (gate G5).
5. The gates dashboard (Lab page, `GET /v1/gates`) shows G0–G6 from stored evidence.

## 5. Backup and recovery

- **State.** All state is in `data/runtime/`:
  - `nafs.sqlite` holds conversations, replies, decisions, audits, runs and feedback;
  - `traces/trace.jsonl` is the append-only trace;
  - `gate_calibration.json` and `gate_params.json` hold the gate's calibration and parameters;
  - `verifier_rates.json` holds the measured verifier rates;
  - `kb/` holds the originals of every knowledge base's documents, and `surreal/` SurrealDB's store (passages, vectors, the graph) and its root password; the two must be backed up together (`scripts/serve_surreal.sh stop` first, or export with `surreal export`).
- **Backup.** Back up with `sqlite3 data/runtime/nafs.sqlite ".backup backup.sqlite"` while running; WAL mode makes this safe.
- **Restore.** Stop the gateway, replace the files, and start it again.
- **Models.** Model files are reproducible from `config/models.manifest.json`, which pins the revision and SHA-256 of each file.
