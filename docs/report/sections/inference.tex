\section{Inference on Four Cores}
\label{sec:inference}

The reference machine is an Intel Core i3-8100: four cores, no simultaneous
multithreading, AVX2 and FMA, no AVX-512, 32\,GB of dual-channel DDR4. A
multi-threaded streaming read reaches 12.9, 17.2, 18.4 and 19.5\,GB/s with one
to four threads. By Proposition~\ref{prop:roofline} decode speed is that
bandwidth over the bytes read per token (1{,}094\,MB for \Sone, 2{,}503\,MB for
\Stwo), and prefill is bound by arithmetic. Table~\ref{tab:measured} gives
the baseline throughput. Everything in this section follows from one fact:
\emph{decode is memory-bound and prefill is compute-bound}, so the gains are in
not repeating work, not in more threads.

\subsection{The engine}
\label{sec:engine}
The default backend is Smiley Core, our own CPU inference engine: a Rust
library with a GGUF loader, a byte-level BPE tokenizer, the Qwen forward
passes with AVX2 and FMA kernels, an F16 or int8 key--value cache, grouped
online-softmax attention, and telemetry that reports the bytes moved per
token beside the tokens per second, so that a run can be checked against the
memory roofline. A thin server exposes it through the same OpenAI-compatible
contract as \texttt{llama-server}, with log-probabilities for the gate,
top-$k$ and min-$p$ sampling, and a reasoning budget enforced by closing the
reasoning span and continuing the turn. The engine's phase split puts 86 to
97\,\% of decode in the matrix products and the output head; sampling is 0.1
to 0.3\,\% and attention 1 to 3\,\% at these context lengths. It runs within
60 to 95\,\% of the machine's bandwidth.

\textbf{Three threads, not four.} Three decode threads beat four in all six
interleaved pairs ($+4\,\%$ on \Sone, $+8\,\%$ on \Stwo\ at the median), while
cold prefill is 16 to 17\,\% slower at three. On a shared host the fourth
worker is the one the scheduler preempts, and every matrix product waits for
its slowest worker. Decode dominates a request and most prompts are cache
hits, so three is the default; it also leaves a core for the sandbox and the
gateway.

\textbf{A prefix store.} A session with a single cache benefits only when a
prompt follows a conversation with the same beginning; alternating a chat
prompt and the agent's prompt prefilled the latter in full each time. The
engine keeps the cache of each finished conversation as a snapshot (114 to
147\,KB per position, 768\,MB per model, least recently used evicted) and
restores the one that shares the longest beginning with the new prompt, in
the manner of prefix-sharing caches \cite{zheng2024sglang}. The answers are
byte-identical with the store on and off.

\textbf{Several users in one pass over the weights.} A decode step reads
every weight once, so serving $n$ users one after another reads the model $n$
times where one pass would do. Decode is bound by memory (19.5\,GB/s) and not
by arithmetic (about 460\,GFLOP/s), and Q4\_K needs 0.56 bytes per weight, so
the roofline ridge sits near seven rows: up to about seven users, another row
costs almost no extra time. The forward pass takes a position and a cache
\emph{per row}; rows of different users share one read of the weights while
each attends only to its own history, one row at a time, so a user's logits
are bit-identical to a solo run's. A slot scheduler runs either one chunk of
one prompt or one token for every ready user in a step, in the manner of
vLLM's serving core \cite{kwon2023pagedattention}, and the prefix store is
shared by all slots.

\textbf{A kernel guard.} Updating the engine once produced a fourfold decode
slowdown with byte-identical kernels: a helper built with
\texttt{std::array::from\_fn} was inlined or not depending on how much
unrelated code the crate contained, which put a function call inside the dot
kernel (679\,ns per row against 96). A kernel whose speed depends on an
optimiser decision about code elsewhere has to be guarded by a benchmark; one
is now part of the crate.

\subsection{Batching and context depth}
\label{sec:batching}
A server that decodes its slots in one batch makes a few more streams cheap,
until compute saturates. Let $c(N)$ be the cost of a batch of $N$ streams in
units of one stream. Table~\ref{tab:batch} shows that the gain falls with
context: from 2.7$\times$ to 1.5$\times$ for \Stwo, and a repair prompt (the
earlier candidate and the verifier's evidence) is about 1{,}600 tokens deep.

\textbf{One request with $n$ choices.} Candidates sent as separate requests
each prefill the whole prompt, and prefill gains nothing from batching. With a
703-token prompt and a 24-token answer one request takes 31.7\,s, four
separate concurrent requests 124.5\,s and one request with $n=4$ 39.1\,s: the
server prefills once and forks the cache. Every multi-candidate round is sent
this way, and each choice is verified as its own stream ends.

\textbf{When does a concurrent round pay?} Take $R+1$ rounds, one-attempt
success probability $p$ and independent candidates. The verified answers per
single-attempt time are
\begin{equation}
U(N)=\frac{1-(1-p)^{N(R+1)}}{c(N)\sum_{k=0}^{R}(1-p)^{Nk}} .
\label{eq:util}
\end{equation}
\begin{proposition}[Limits of widening] \textnormal{[exact]}
\label{prop:wide}
As $p\to0$, $U(N)/U(1)\to N/c(N)$: widening pays iff the batch is cheaper than
the same streams in series. As $p\to1$, $U(N)/U(1)\to 1/c(N)<1$: it never pays.
\end{proposition}
\begin{proof}
For small $p$, $1-(1-p)^{N(R+1)}\approx N(R+1)p$ and the sum tends to $R+1$, so
$U(N)\approx Np/c(N)$ and $U(1)\approx p$. For $p\to1$ numerator and sum tend
to 1. \qed
\end{proof}
With the short-context costs the policy widens for $p\le0.48$; with the
1{,}600-token costs it widens only for $p\le0.07$. Concurrent hedging on
\Stwo\ is implemented and off (Section~\ref{sec:eval:negative}).

\textbf{Cheap samples before the expensive model.} Where batching is cheap
(\Sone, short context) and the verifier is exact, the cores are better spent
\emph{before} \Stwo. When a draft fails its exact check, four \Sone\ samples
are drawn in one request, each verified as it finishes, and the first that
passes is kept.
\begin{proposition}[Rescue break-even] \textnormal{[exact]}
\label{prop:rescue}
Let $f$ be the share of requests whose draft fails, $r$ the share of those
that a sample rescues, $\rho$ the cost of the rescue stage and $E$ the cost of
an escalation. The saving per request is $f\,(rE-\rho)$, positive iff
$r>\rho/E$.
\end{proposition}
The agreement samples of the gate are fused into the draft's batch for the
same reason: drawn after the draft they cost $1+c(2)=2.33$ draft times, in its
batch $c(3)=1.78$.

\subsection{The model switch}
Both models are resident, each in its own process with its own mapped
weights, so a switch inside a request is routing plus a warm prefix: there is
nothing to freeze, copy or reload. From the gate's decision to \Stwo's first
reasoning token takes 0.4 to 1.4\,s (median 0.85\,s over six escalated
requests). When both servers decode at once each keeps about half to two
thirds of its solo rate and the pair writes 7.1 to 7.8 tokens/s together
under every thread and polling setting tried; the cores are the bottleneck
and no co-scheduling policy was worth building. At the reasoning budget the
server continues the turn with the reasoning so far as the assistant's
prefix; the prefix must repeat the generated text exactly, or every reasoning
token is prefilled again (5 tokens and 0.2\,s when exact, against 108 tokens
and 2.2\,s at a budget of 200 when one newline differed).

\subsection{Alternative backends}
\texttt{llama-server} keeps four things the default engine's server does not
expose: decoding grammars, $n$-choice requests, a raw continuation endpoint
and four parallel slots per model. With Smiley Core as the backend the rescue
and the cascade therefore have one candidate instead of four, the agent
relies on the free-text parser, and the adaptive reasoning exit is off;
llama.cpp is one command away and is the choice for a workload dominated by
the code agent. vLLM's CPU backend runs the same API in a Linux container; on
an AVX2-only host it must run in FP32 with a small context and is a
portability profile, not a speed contest. Ollama is not supported because its
OpenAI endpoint does not return log-probabilities, which the gate requires.
