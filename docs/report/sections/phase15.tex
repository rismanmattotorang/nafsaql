\section{Phase 15: Smiley Core as the Third Inference Backend}
\label{sec:phase15}

Phase~15 (1 November 2026) integrates Smiley Core, the owner's own CPU inference engine from the Smiley project, as a third
backend beside llama.cpp and vLLM. The research note is \texttt{docs/research/smiley\_backend.md} and the decision is
\texttt{docs/decisions/009-smiley-backend.md}.

\subsection{The engine}

Smiley Core is a Rust library of about 8,500 lines with one dependency: a GGUF loader, a byte-level BPE tokenizer checked
against \texttt{llama-tokenize}, the \texttt{llama}, \texttt{qwen2} and \texttt{qwen3} forward passes with AVX2 and FMA
kernels, an F16 or int8 KV cache, a chat session with the models' own templates (including Qwen3's \texttt{enable\_thinking}),
prompt-lookup and DSpark speculative decoding, and telemetry that reports the bytes moved per token beside the tokens per
second, so a run can be checked against the machine's memory roofline rather than taken on faith. It decodes one stream per
session: no batching across requests, no constrained sampling, no raw continuation. Both \Sys{} models pass its compatibility
probe.

\subsection{Integration}

The gateway already speaks one OpenAI-compatible API to two kinds of server, so the integration is a server around the engine
and a configured pair. The engine is vendored into the workspace (\texttt{rust/crates/smiley-core}, since \texttt{third\_party/}
is not under version control) with two marked additions: a continuation prefix on the session (what the assistant has already
written, appended after the template's assistant header) and the sampled token's log-probability on each emitted token.
\texttt{nafs-smiley-server} serves one model per process: \texttt{POST /v1/chat/completions} streamed or not, with
\texttt{usage} and llama-style \texttt{timings} plus a \texttt{smiley} block carrying the bytes moved; \texttt{/v1/models} for
the health check; \texttt{/metrics}. The system message becomes the session's system text, earlier exchanges are seeded as
history, the last user message is the turn; the session is reset per request and reuses its cache prefix when the prompt shares
it. \texttt{enable\_thinking} maps to the session's thinking switch. The reasoning budget is enforced by counting reasoning
tokens and, at the budget, replanning the turn with the reasoning so far plus \texttt{</think>} as the assistant's prefix, so
the answer follows as under llama-server's budget forcing; the cache prefix is reused and only the forced tail is prefilled.
\texttt{logprobs} are served for the gate's fixed rule. Requests with \texttt{n > 1} or a grammar are refused, so on this
backend the gateway runs without the rescue batch, the harness grammar and the raw-continuation exit, as it does on vLLM.
\texttt{[backends.smiley]} configures the pair (:8201, :8202, one stream each); \texttt{make up} builds and serves it; it is the
default backend after the comparison below, and \texttt{make up-llama} switches the gateway to llama.cpp, warm-first.

\subsection{Measurements}

Two comparisons ran on the shared four-core host, the arms interleaved and the load recorded per request
(\texttt{scripts/smiley\_ab.py}, \texttt{scripts/backend\_ab.py}).

\textbf{The engines alone}, with identical greedy requests (12 pairs per model). Decode speed was 14.3 tokens/s for Smiley Core
against 12.6 for llama.cpp on System~1 and 7.4 against 6.6 on System~2; Smiley Core was faster in 10 of 12 and 11 of 12 pairs,
by a median of $1.13\times$ and $1.14\times$. Its first token is later on System~1 (0.64\,s against 0.11\,s: the session is reset
and the prompt replanned per request) and earlier on System~2 (1.60\,s against 1.85\,s). Answers are identical in 12 of 12
System~1 pairs and 9 of 12 System~2 pairs. The bytes moved per token (1.09\,GB and 2.50\,GB) put both models on the memory
roofline at 15.6 and 18.5\,GB/s, so the gain is the engine's own overhead and not a different algorithm.

\textbf{The whole service}, with the gateway switched between the backends before every request (warm-first) and the same twelve
prompts sent in Auto mode (four maths with a reference answer, three code with hidden tests, two JSON schema, three open or
factual):

\hline
 & llama.cpp & Smiley Core \\
\hline
Checked answers (9 checkable) & 9/9 & 9/9 \\
Wall time, median per request & 17.9\,s & \textbf{9.7\,s} \\

Smiley Core was faster in 10 of the 12 pairs (one-sided sign test $p=0.02$), by a median of $1.59\times$. The code agent's first
run on Smiley Core failed at the 900\,s deadline and exposed a harness defect that is not the engine's: without a grammar the
harness reads free text, and Qwen3-1.7B writes the patch without its \texttt{*** Begin Patch} line (the same on llama.cpp when
unconstrained), which the parser read as no action. The patch finder and the stream cut now accept a patch that starts at
its first file section (unit-tested). After the fix both backends verified the task: 263\,s on Smiley Core, 53\,s and 291\,s in
llama.cpp's two runs, which one run per backend cannot rank.

\subsection{Sampling and the acceptance suite}

llama-server samples with \texttt{top\_k}\,=\,40 and \texttt{min\_p}\,=\,0.05 by default; Smiley Core had temperature and top-p only,
and System~2 on it wrote 1,025 reasoning tokens (the budget) where llama.cpp wrote 274 on the same question. The engine gained
both filters (off by default in the engine, on at llama-server's values in the server, unit-tested). Over three seeds of one
GSM8K question Smiley Core then wrote about 12\,\% more reasoning tokens (1,037 against 925 on average) in about 16\,\% less
wall time (132\,s against 157\,s). The nine MVP acceptance tests pass on Smiley Core (9/9); on a host still loaded by the
preceding sweep two of them failed on time (first token 9.0\,s against 2\,s; slow path 309\,s against 240\,s) and passed on
a quiet one (0.06--1.7\,s; 193--195\,s). The slow-path budget is within reach on Smiley Core only on a quiet host: System~2
decodes 7.4 tokens/s and a 1,024-token reasoning span is 138\,s of it. The full sweeps on the final build: 309 Rust tests,
contract, security 26/26, Rooms 59/59, end to end 65/65, harness sweep 53/53 (two checks assumed llama.cpp's four slots and
now follow the active backend).

\subsection{Summary}

On the criterion fixed before the run, the time to a checked answer through the gateway with the answers equally
checked, Smiley Core wins for one user at a time and is the default backend (\texttt{backend.active = "smiley"}; decision~009).
What it gives up is what the engine does not have: one stream per model, so a second concurrent request waits, the rescue
and the cascade have one candidate instead of four, there is no grammar (the agent relies on the hardened free-text parser) and
no raw continuation (the adaptive exit is off). llama.cpp keeps all four and is one command away (\texttt{make up-llama} or the
System page); it is the choice for a shared deployment or a workload dominated by the code agent.
