\section{Architecture}
\label{sec:arch}

\subsection{Design principles}
Four principles follow from Section~\ref{sec:math}. (1)~\emph{The gate is
derived, not tuned}: the controller compares a calibrated error estimate with
a cost ratio (Theorem~\ref{thm:gate}). (2)~\emph{Acceptance needs evidence}:
no answer is marked verified unless an exact verifier accepted it; consensus
and judge scores are assurance levels, not proofs
(Theorems~\ref{thm:precision} and \ref{thm:plurality}). (3)~\emph{Every loop is
bounded}: $N$, $R$ and the thinking budget are configuration limits enforced
by the gateway (Lemma~\ref{lem:termination}). (4)~\emph{Self-knowledge is
audited}: the self-model is built from traces plus a random audit stream and
reports unmeasured capabilities as such (Proposition~\ref{prop:audit}).

\subsection{Request lifecycle}
Fig.~\ref{fig:flow} shows one request and Fig.~\ref{fig:nafs-automaton} its
state automaton. The context manager assembles the prompt from the
conversation, any retrieved memory and, when a knowledge base is selected, its
passages, each with provenance. \Sone\ produces a draft in non-thinking mode.
The gate computes features: mean and minimum token log-probability of the
draft, the lowest window of consecutive tokens, agreement among $k$ cheap
samples, the domain class, whether the turn repeats the previous one, and, for
verifiable tasks, the verifier's verdict on the draft. A verifiable task whose
draft fails verification is never eligible for the keep branch; before it is
escalated, four cheap \Sone\ samples are drawn in one request and the first
that passes the exact check is returned (Section~\ref{sec:inference}). On
escalation, \Stwo\ runs draft-blind in thinking mode with budget $b$ and
sequential sampling: each candidate is verified and the first accepted one is
returned; a rejected candidate's evidence (failing test, counterexample, schema
error) is fed into the next round, up to $R$ rounds. If the budget is
exhausted the reply is an explicit abstention with the best candidate and an
uncertainty notice. Every reply carries an \emph{assurance level}:
\texttt{verified} (an exact verifier passed), \texttt{consensus} (soft
agreement only), \texttt{unverified} (a kept draft on a non-verifiable task) or
\texttt{abstained}; the interface shows them as \emph{Checked},
\emph{Cross-checked}, \emph{Not checked} and \emph{Not sure}. The gate's
decision record and the trace of the loop are written to the audit ledger.

\subsection{Components}
\label{sec:components}
The system is one Rust workspace of thirteen crates and one static gateway
binary (Fig.~\ref{fig:arch}).
\begin{itemize}
\item \textbf{Gateway (\texttt{nafs-gateway}).} HTTP API with an
OpenAI-compatible chat endpoint, SSE streaming of tokens and of controller
events, WebSocket chat rooms, authentication, rate limits, Prometheus metrics
and the embedded web interface (Fig.~\ref{fig:ui-chat}).
\item \textbf{Orchestrator and gate (\texttt{nafs-core}).} The automaton, the
gate, sequential verified sampling, budget forcing, timeouts and fallbacks.
\item \textbf{Inference backends.} Two model servers behind one
OpenAI-compatible contract. The default is our own engine, Smiley Core, served
by \texttt{nafs-smiley-server}; \texttt{llama-server} and vLLM's CPU backend
are alternatives switched at run time (Section~\ref{sec:inference}).
\item \textbf{Verifiers (\texttt{nafs-verify}).} Exact: a code sandbox (no
network, CPU, memory and wall-clock limits; namespaces and seccomp on Linux,
Seatbelt on macOS), numeric and symbolic mathematics, JSON Schema validation,
and Lean~4. Soft: a rubric judge (the \Stwo\ model in non-thinking mode at
temperature~0) and sample consensus. Each publishes its measured
$(r,\varphi)$.
\item \textbf{Agent harness (\texttt{nafs-harness}).} A bounded code agent
whose runs end only when the exact verifier accepts or the budget is spent
(Section~\ref{sec:harness}).
\item \textbf{Knowledge (\texttt{nafs-kb}) and memory (\texttt{nafs-memory},
\texttt{nafs-memorilla}).} Document readers, the passage index, the graphs, the
check of an answer against its passages, the store of verified answers, the
notes of earlier conversations and the memory-token module
(Sections~\ref{sec:knowledge} and~\ref{sec:memory}).
\item \textbf{Audit ledger.} Per-domain calibration tables (escalation rate,
calibration error of $\hat e_1$, verifier acceptance rates, latency quantiles)
aggregated from traces and the audit stream, keyed by model hash; it feeds the
quality page, drift alerts (a two-sided CUSUM per domain \cite{page1954cusum}
with a shuffled negative control) and the gate's recalibration.
\item \textbf{Evaluation and load testing (\texttt{nafs-eval},
\texttt{nafs-bench}).} Dataset loaders, paired statistical tests, a laboratory
that runs each way of combining the two models as a \emph{policy} on identical
tasks, and a load generator.
\end{itemize}

\subsection{Drawing an answer}
\label{sec:render}
Answers are drawn by one dependency-free module (\texttt{render.js}) that maps
the model's Markdown to safe HTML; it has no build step and runs under Node, so
it is tested without a browser (142 checks, including every prefix of a rich
answer, which must render without error while the answer streams). Tables keep
their alignment, right-align numeric columns, and can be copied as
tab-separated text. Code is highlighted by a small tokenizer and long blocks
collapse. LaTeX becomes MathML Core, which current browsers draw natively
(fractions, roots, sums and integrals with limits, matrices, cases, aligned
blocks); a dollar amount such as ``\$5 and \$6'' is not read as a formula. A
Mermaid subset (flowcharts with seven node shapes, subgraphs and edge labels;
sequence diagrams; pie charts) is laid out in layers, with long edges routed
through the layers they cross, and drawn as inline SVG that can show its source
or be saved. Anything outside the subset, or that does not parse, stays a code
block. All model text is escaped and nothing but a checked colour reaches a
style, so the page policy (\texttt{script-src 'self'}) is unchanged. KaTeX and
Mermaid were not vendored: both are downloads, and the subset covers what the
model writes in practice (Fig.~\ref{fig:ui-rich}). The knowledge graph
(Fig.~\ref{fig:ui-graph}) is a force layout with collision and communities, node
size by mentions and colour by group; hovering lights a thing's neighbourhood,
choosing it shows the sentences that state each relation, and a double tap opens
what is around it.

\subsection{Model profiles}
\label{sec:models}
The reference profile uses two dense Qwen3 checkpoints \cite{qwen2025qwen3},
one per role: Qwen3-1.7B (Q4\_K\_M, 1.3\,GB) as \Sone\ with thinking off, and
Qwen3-4B-Thinking-2507 (Q4\_K\_M, 2.5\,GB) as \Stwo. Dense grouped-query
attention has the most mature CPU kernels and official GGUF files exist. The
judge is the \Stwo\ model in non-thinking mode, and embeddings come from
Qwen3-Embedding-0.6B (Q8\_0). All are Apache-2.0. Two alternatives are
supported by configuration: a single switchable Qwen3-4B serving both roles,
which halves resident memory at the price of a slower fast path, and a
Qwen3.5 pair, whose \Sone\ candidate was measured and not adopted
(Section~\ref{sec:eval:negative}).

\subsection{Deployment}
The deployment is a single node: one gateway process, two model servers, an
embedding server, a sandbox runner, SQLite for conversations and the ledger,
and SurrealDB as the source of truth for the knowledge base. No request
leaves the machine. The gateway switches between backend sets at run time,
warm-first: every constant prompt prefix is primed on the new servers before
one atomic swap, requests in flight finish on the pair they started on, and a
new request finds a warm cache (about 1\,s to the first token against 9.8\,s
cold). A GPU profile replaces the model servers with vLLM on CUDA and leaves
every other component unchanged; it was not exercised here.
